# Bug Fixes — 08/04/2026

Bugs encontrados y corregidos durante la sesión de testing con `testing_apis_service.py`.

---

## 1. `Attribute` sin `__eq__` / `__hash__` — comparación por identidad

**Archivo:** `models.py` — clase `Attribute`

**Problema:** Python por defecto compara objetos por identidad (`is`). Al cargar el mismo atributo dos veces desde la DB (por ejemplo, una vez en el producto y otra vez en el `AttributeRepo`), se obtenían dos objetos distintos. Las comparaciones de sets (`impl_attributes != needed_attributes`) fallaban aunque los atributos representaran el mismo registro.

**Síntoma:** `create_variant_by_implementations` siempre retornaba `implementations_invalid` aunque las implementaciones fueran correctas.

**Fix:** Se agregaron `__eq__` y `__hash__` a `Attribute` usando `self.id` como clave de igualdad.

---

## 2. `Product.add_dinamic_attribute` sin guard de `is_static`

**Archivo:** `models.py` — método `Product.add_dinamic_attribute`

**Problema:** La versión de `Category.add_dinamic_attribute` validaba que el atributo no fuera estático (`is_static`) lanzando `ValueError`. La versión de `Product` no tenía esa validación.

**Síntoma:** Agregar un atributo estático como dinámico a un producto no lanzaba error.

**Fix:** Se agregó el guard al inicio del método:
```python
if attribute.is_static:
    raise ValueError("El attributo que se quiere incertar es estatico")
```

---

## 3. `Category._add_attribute_variant_impact_check` incluía productos sin variantes

**Archivo:** `models.py` — método `Category._add_attribute_variant_impact_check`

**Problema:** Al agregar un atributo dinámico a una categoría con productos que no tienen variantes, el método marcaba esos productos como "en riesgo" y pedía implementaciones. Un producto sin variantes no necesita cubrir ninguna variante con el atributo.

**Síntoma:** `CategoryService.add_dynamic_attribute` retornaba `needs_implementations: True` incluso cuando el producto no tenía variantes.

**Fix:** Se filtra la lista `impact` para incluir solo productos con al menos una variante:
```python
impact = [p for p in impact if p.variants]
```

## 4. `Product.add_product_implementation` silenciaba `ValueError`

**Archivo:** `models.py` — método `Product.add_product_implementation`

**Problema:** El método envolvía la llamada a `_check_implementation` en un `try/except ValueError` que capturaba el error, lo imprimía por stdout, y retornaba `False` sin relanzar. La capa de servicio no chequeaba el valor de retorno y guardaba el producto igual.

**Síntoma:**
- Agregar una implementación con atributo no suscripto no lanzaba `ValueError`.
- Agregar una implementación con tipo de dato incorrecto no lanzaba `ValueError`.

**Fix:** Se eliminó el bloque `try/except` y se dejó que `_check_implementation` propague el `ValueError` directamente.

---

## 5. `Product.create_variant_by_implementations` ignoraba valor de retorno de `check_value`

**Archivo:** `models.py` — método `Product.create_variant_by_implementations`

**Problema:** El chequeo de tipo de valor para cada implementación solo capturaba `ValueError`. Sin embargo, para atributos de tipo `enum`, `check_value` retorna `False` (no lanza excepción) cuando el valor no pertenece a los valores posibles. El retorno booleano no se chequeaba.

**Síntoma:** Crear una variante con un valor de enum inválido (ej. `"Z"` en un enum `["A", "B"]`) creaba la variante sin error.

**Fix:** Se agrega verificación del retorno booleano:
```python
if not i.attribute.check_value(i.value):
    print(f"Error en tipo: valor inválido para '{i.attribute.name}'.")
    return None
```

## 6. Tests con códigos de producto hardcodeados — falla en re-ejecuciones

**Archivo:** `testing_apis_service.py`

**Problema:** Varios tests usaban códigos de producto fijos (ej. `"CS-DEL-PROD"`, `"PAI-OK-001"`). Como las operaciones hacen `commit`, los datos persisten entre ejecuciones. La segunda ejecución fallaba con `UniqueViolation` en la constraint `product_code_key`.

**Fix:** Se modificó `mk_prod` para generar un código único por defecto usando `uuid4().hex[:8]`. Los tests que usaban códigos hardcodeados pasaron a usar el código auto-generado.

---

## 7. Tests de `add_implementation` con setup incorrecto

**Archivo:** `testing_apis_service.py` — clase `TestProductAddImplementation`

**Problema:** Los tests creaban primero el producto y después llamaban a `CategoryService.add_static_attribute`. Al haber un producto sin implementación, el service retornaba `needs_implementations: True` sin persistir el atributo en la categoría. Al llamar luego a `add_implementation`, el atributo no estaba suscripto y el chequeo fallaba.

**Síntoma:** `test_success_subscribed_via_category`, `test_duplicate_raises`, y `test_wrong_type_raises` fallaban porque la categoría no tenía el atributo suscripto.

**Fix:** Se reordenó el setup: el atributo se suscribe a la categoría **antes** de crear el producto, garantizando que cuando el producto se crea la categoría ya tenga el atributo.
